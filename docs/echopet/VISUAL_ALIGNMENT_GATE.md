# EchoPet Visual Alignment Gate

This document narrows the current work target to visual alignment. Behavior work
can continue only after the currently implemented screens and source-backed
assets pass this gate, or after the open visual gaps are explicitly accepted as
temporary substitute art.

Visual alignment has three layers:

1. Runtime source truth: C/C++ bitmap rows, composed sprite frames, menu icon
   drawing, layout anchors, and screen state. PNG/JPG/GIF files are never
   runtime resources.
2. Source-side projection: `analysis/screen_simulator/out/*.png`, generated by
   compiling the real `drawEchoPet(...)` path against the host display shim.
3. Hardware proof: photos or direct observations on T-Echo-Lite. Simulator
   output cannot prove e-paper ghosting, whitening, missed frames, orientation,
   BUSY timing, or real button feel.

## Required Outputs

The gate covers both supported screen profiles:

- `compact`: 128x64 canvas, 32x64 left rail, 64x64 main playfield, 32x64 right
  rail.
- `large`: 192x176 canvas for the 176x192 device orientation, 32x176 side
  rails, 128x128 main playfield, and one top/bottom information line at most.

- `fixed_menu_icons_proof_x*.png`

## Acceptance Rules

- The firmware resource route stays source-backed: C/C++ bitmap arrays,
  composed frame tables, and programmatic drawing only. Runtime code must not
  load PNG/JPG/GIF/BMP files.
- Both profiles render at the expected dimensions.
- The two side rails contain only the fixed ten Connection-style menu slots:
  health, food, toilet, connection, attention, discipline, medicine, lights,
  friends, and games/activity.
- Selection state is visible, and cycling through the fixed icons changes the
  selected slot without changing the icon set.
- The center playfield is bounded and non-empty on every implemented preview.
- Large-profile top and bottom bands are single-line utility bands. They must
  not become multi-row debug/status HUDs.
- Compact-profile screens may place one short title/result string inside the
  64x64 playfield, but text must not make the pet/action unreadable.
- Pet sprites, props, food, medicine, cleanup tools, shop booth, game objects,
  family/friend portraits, and catalog icons must stay inside their intended
  scene area.
- Egg, pet, and action compositions must use named frame/part definitions so a
  future pet can be replaced by redrawing frames rather than changing gameplay
  code.
- "Has a hook" is not enough for visual alignment. A 160-row item catalog or
  50-row character catalog is visually aligned only when the rows have
  recognizably distinct low-resource artwork or an accepted substitute-art
  contract.
